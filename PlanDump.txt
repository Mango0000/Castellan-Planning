# Product Concept: Unified AI Coding Platform

A self-hosted AI development environment built around OpenAI Codex, with an architecture that allows additional coding agents to be integrated later.

The idea is to build your own alternative to the interfaces of Cursor, Replit or Claude Code, but with one important difference: you own the platform, the project infrastructure and the agent integration layer.

For the first version, you only need Codex. However, the architecture should make it possible to add Claude Code, OpenHands, OpenCode or custom agents without rebuilding the application.

## 4. How the Codex integration works

The initial user journey:

1. Create a project
   User creates a project or connects a GitHub repository.
2. Create a workspace
   Your backend prepares a persistent project directory and Git working environment.
3. Start Codex
   The Codex adapter starts or connects to an App Server session with the correct workspace and permissions.
4. Send a task
   Your frontend sends a message through your backend to Codex.
5. Stream events
   Codex sends structured events. Your backend normalizes them and forwards them to the dashboard.
6. Inspect changes
   Your platform displays file changes, terminal activity, approvals and Git diffs.
7. Continue working
   Users can send follow-up instructions, restart sessions or inspect the project in their own IDE.

The native Codex application can also work with the same repository. However, native app conversation synchronization should be treated as a separate integration requirement, not assumed just because the files are shared.

## 6. Infrastructure for your IONOS VPS

Your current VPS:

- 2 vCores
- 2 GB RAM
- 90 GB NVMe

I would use it initially for the lightweight control plane, not for executing coding agents.

| Service | Location |
| --- | --- |
| Next.js | IONOS VPS |
| FastAPI | IONOS VPS |
| PostgreSQL | IONOS VPS, carefully sized |
| Codex App Server | Separate execution machine |
| Docker workspaces | Execution machine |
| Git repositories | Persistent workspace storage |

You could start with one additional x86 mini-PC or a small cloud server with 8–16 GB RAM.

I would choose x86 rather than Raspberry Pi for this use case because Docker compatibility and development tooling are generally simpler.

Also, Codex model inference is handled through the configured OpenAI service, so you do not need a powerful GPU for the agent itself.

## 8\. What makes this platform special?

I wouldn't position it as just another AI chat interface.

The real value is that it combines:

- A persistent development environment.
- A unified interface for coding agents.
- Full visibility into agent execution.
- Project and workspace management.
- Extensible integrations.
- The ability to change the underlying agent without losing your projects.

In the long run, users could even run different agents on the same project: Codex implements a feature, Claude reviews it, and another agent writes tests.

That's where this concept becomes particularly interesting.

## My recommendation: three architectural principles

1. Codex-first, not Codex-only. Build the first integration deeply, but never make Codex-specific assumptions in the main application.
2. Workspace ownership belongs to your platform. An agent should never own the only copy of a project or its history.
3. Treat agent execution as a secure, isolated service. Never expose a Docker socket, arbitrary terminal or agent credentials directly to the browser.

One additional distinction worth preserving: your platform should own project and task history, while each provider retains its own native conversation state. Store the provider's session/thread identifier so you can resume sessions where supported.

The product vision in one sentence:

A self-hosted, extensible AI coding workspace that lets you manage projects, run Codex, monitor its work in real time, and eventually switch between different AI coding agents without changing your development environment.

This is the foundation I would build.
