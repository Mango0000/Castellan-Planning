01

The product in one page

Vision · promises · what it isn't ›

Strip away the tooling and the product makes three promises: your code stays yours, you can see what the agent is doing, and you can replace the agent without losing anything.

01
◇

Own the workspace

Repositories, branches, tasks and history live in your infrastructure. Delete the agent provider tomorrow and your project is still there, with every change accounted for.

02
⇄

One UI, many engines

Codex ships first, one agent at a time. Claude Code, OpenHands and OpenCode come later through one adapter contract — not four special cases bolted into the shell.

03
◉

Live, not theatre

Every progress line comes from a real app-server event: a tool call, a file change, an approval request, a test result. No fake spinners, no invented percentages.

04
✓

Safety you can audit

Risky operations stop and ask. Every decision is a row in the database, scoped to a turn, a task or a project — so “why did it run that?” has an answer.

What it is — and what it deliberately isn't

It is

  • A personal cloud dev environment for one motivated developer.
  • A durable queue of agent tasks on real git branches — plus a scratch chat for questions that need no repo.
  • An audit trail of everything an agent did, and why.
  • A thin, honest shell over the Codex App Server protocol.

It isn't

  • A browser IDE that beats VS Code. Don't try.
  • A Cursor rival for inline tab-completion.
  • A multi-tenant SaaS in V1 — the auth boundary matters (see 02.09).
  • A GPU box. Inference happens remotely; your hardware just runs processes.
One sentence

A self-hosted, extensible AI coding workspace where projects, tasks and history belong to you, quick questions get a scratch chat, and the agent is a replaceable execution provider.

The original draft frames this well. The rest of this document is about making it buildable: the missing data model, the scope cuts, and the decisions that keep a 2 vCPU VPS alive.

02

What I changed from the draft

Eleven decisions, and why ›

Both documents describe the same product, and the architecture is right. The weak spots are scope and the missing data model. Eleven changes turn the blueprint into a build plan.

Data

01 · Make the Task the object

The draft uses “task”, “session” and “conversation” interchangeably. Define one durable Task: workspace + branch + provider thread + budget + state. Chat is a view of the thread, not the record.

Data

02 · Persist events, stream views

Streaming is not storage. Append every normalized event to Postgres. The UI then replays a task after a refresh, supports audit, and survives a runner restart.

Scope

03 · No code editor in V1

An editor is weeks of polish for something VS Code already does better. Ship a read-only viewer with line numbers and an Open in VS Code SSH link.

Scope

04 · Terminal: output now, PTY later

The draft disagrees with itself — PlanDump puts Terminal in V1, the HTML puts it in Phase 2. Resolve it: V1 shows live command output; an interactive shell lands in V1.5.

Safety

05 · One active task, period

V1 runs one agent at a time; queue the rest per workspace. Worktrees and a concurrency limit come in V1.5, once the single-agent loop is boring. Two agents in one worktree is a merge-conflict generator.

Architecture

06 · Runner dials out, never listens

App-server's WebSocket transport is documented as experimental and unsupported, and non-loopback listeners accept unauthenticated connections by default. Keep app-server on stdio behind the runner; expose nothing.

Infra

07 · Skip Redis for V1

On a 2 GB control plane, Redis is ~100 MB you would rather spend elsewhere. Postgres SKIP LOCKED is a perfectly good queue until there is more than one worker.

Product

08 · Put money on the task

Token spend is the one number that can go wrong silently. Show tokens and estimated cost in the task header, and cap each task's budget with a hard stop.

Legal

09 · Mind the auth boundary

App-server login is for local and open-source use; per OpenAI's docs it has never been permitted for commercial or hosted services. Personal instance today — own API key or Sign in with ChatGPT if you ever host it for others.

UX

10 · The sidebar is the dashboard

A dashboard page is a place you forget to check. Put working sessions, workspaces and temporary chats in one rail that never leaves the screen; the middle pane is always the thing you selected. A second rail on the right holds files, diff, preview and terminal, and both rails collapse independently.

Product

11 · Workspace dashboards are data

A dashboard is a JSON widget list, not generated HTML. The agent edits that list through one narrow tool; the UI renders a fixed vocabulary of widgets. Agent-customizable without letting the agent run arbitrary UI code.

What the draft got right

The adapter abstraction, the worktree guidance, event normalization, approval handling and the two-box split are all correct. This version keeps them and adds the missing data model, the budget guard and an explicit deployment boundary.

Positioning: don't rebuild the desktop app

Vibe Console — the first moodboard link in the draft — already runs twelve agent CLIs side by side in a native Mac window, with local projects, git and usage limits. Competing on “many agents in one window on my laptop” is a losing race you don't want to run.

Your wedge is the part a desktop app structurally can't give you: web access to durable tasks, history that survives your laptop closing, approvals with an audit trail, and more than one person using the same environments.

One thing to verify before building

The App Server protocol is the backbone of this design. Generated schemas are version-specific, so pin the Codex CLI version on the runner, generate JSON Schema at build time, and keep a contract test that fails loudly on protocol drift. The details below reflect the public docs as of this writing.

Rail · dashboard · context ›

Two rails, one agent

The left rail is navigation; the right rail is evidence. The Explorer starts at the workspace root with a location bar; folders expand in place, and clicking a file opens a new tab for code, rendered Markdown, an image or a sandboxed static page. A ＋ menu adds Terminal, Diff or Preview, and tabs close independently. Both rails run full height, resize by dragging the divider, and collapse from their own headers. Browser chrome is a separate wrapper; the app UI has no global title bar. The middle pane never changes: one session, one composer, one approval queue. Each task and temporary-chat row in the left rail carries a small archive button; the rail has a muted Archive link pinned at the bottom with the count inline, no separate header. It asks for confirmation in a centered dialog over a blurred workspace; the Archive view restores or deletes old work, and offers Delete all with its own confirmation.

Every composer carries the same three controls: a Codex model picker, a reasoning effort picker with only the efforts that model supports, and a ＋ context button. The plus offers Upload for local files and Remote for a file browser that starts at the workspace root with a path bar, expandable folders and double-click-to-open; in temporary chats the same dialog switches workspace. Model, effort and attachments are per chat. The model list comes from model/list in the real runner; the mock keeps it in models.js.

V1 scope, stated plainly

The Preview tab opens the workspace's dev-server URL over the tailnet; embedding a proxied page is V2. The Terminal tab is command output in V1; an interactive PTY is the first V1.5 item. The right rail is a real feature — it links out rather than running browser-in-browser.

Workspace dashboards are data

Clicking a workspace opens that workspace's dashboard. The description, dev-server controls, active task, recent changes and pinned commands are widgets. The agent can add, remove and reorder them — not by writing HTML, but by editing a small JSON document owned by the workspace.

The dashboard document, in one widget list 
{
  "version": 3,
  "widgets": [
    { "type": "dev-server", "span": 2 },
    { "type": "active-task" },
    { "type": "recent-changes" },
    { "type": "description", "props": { "text": "Marketing site..." } },
    { "type": "commands", "props": { "commands": ["npm test", "open preview"] } }

}

Known widget types only. Props are data, never markup. The agent gets a dashboard.update tool (or edits .castellan/dashboard.json); the renderer validates against a schema and ignores unknown widgets. Dev-server actions are a fixed start / restart vocabulary, not a shell.

Agent-customizable, not agent-authored

This is the line that makes the dashboard useful without making it dangerous: the agent decides what is on the dashboard, never what code the dashboard runs. The same rule applies to the context rail: files and diffs are rendered from records, not generated UI.

The rest of the surface

⑂

Git, but small

V1: view diff, commit to the task branch, discard the task, open a PR link. V2: branches, worktrees, PR creation, revert an agent commit. Never force-push from the UI.

A pending approval lives inline and as a rail badge, not a full-screen dialog. Scope the decision: once, for this task, or for the project. Deny is always one click away.

A note on the mockups

These are UI hypotheses, not pixel specs. The one rule worth keeping: every visual claim must trace back to an event, a record, or a policy decision. If the UI can't point at the source, delete the element.

How it actually works

Layers · flow · protocol · data model ›

The control plane never runs code. It records what happened and decides what is allowed. Everything else happens on the runner, next to the repository.

The one rule that keeps this simple

If a component can execute a command in a repository, it is not allowed to hold a user session, serve the browser, or accept an inbound connection.

Seven layers

Click a layer for its job, what it owns, and its failure mode.

Web UI

V1
Next.js · App Router

Renders state and captures intent. No secrets, no repository paths, no provider credentials — those stop at the API.

Nevertalks to app-server directly
Failsstale view → reconnect and replay after the last sequence number

One task, end to end

  1. You send a prompt. The API creates a Task (queued) with a budget, a target project and a policy, then offers a job to the queue.
  2. The runner claims it. Postgres SKIP LOCKED, no Redis. It fetches the repo, creates branch task/<slug>, and prepares the workspace path.
  3. It starts Codex. Spawns codex app-server with cwd set to the workspace, sends initialize, then initialized, then thread/start.
  4. The turn begins. turn/start carries the prompt, working directory and sandbox policy. The returned threadId is stored on the task.
  5. Events arrive. Items, deltas and approval requests stream back over stdio. The runner normalizes each one and batches it to POST /internal/events.
  6. The UI follows. The API appends events with a per-task sequence number and fans them out over WebSocket. Steps, logs and diffs update from data.
  7. You decide. An approval becomes a row plus a card. Your choice travels back through the runner as the response to the pending JSON-RPC request.
  8. The turn ends. turn/completed closes the task, records tokens and cost, shows the diff, and offers commit, PR or discard.
Two doors, one pipeline

A workspace task and a temporary chat differ in a few fields: kind, workspace_id, context_folder and expires_at. Everything else — initialize, thread, turn, events, approvals, spend — is identical. A chat uses a scratch directory by default, or mounts one workspace/folder read-only when you attach context. No branch, no commit. Keep as task copies the transcript into a real task once you pick a workspace.

The adapter is a mapping, not a rewrite

App Server already exposes almost everything this product needs. The adapter's job is to normalize events and translate policy — not to re-implement an agent runtime.

Why stdio, not a public WebSocket

OpenAI's docs describe the app-server WebSocket transport as experimental and unsupported, and non-loopback WebSocket listeners currently accept unauthenticated connections by default. So: the runner spawns one app-server process per workspace over stdio, one thread per task, and the runner's own connection to the control plane is outbound-only. Nothing agent-related listens on a network port. App Server docs ↗

Unread is derived, not a flag: a session is unread when last_read_seq < max(events.seq). Opening it advances last_read_seq; an approval is separate state and stays until you decide.

Indexes: events(task_id, seq), tasks(state, created_at). Retention: keep task summaries forever, archive raw events after 90 days.

Auth: httpOnly session cookie, Argon2 password, optional TOTP. The runner uses a per-runner token and a dedicated internal route prefix — never a user session.

The runner loop, compressed 
claim job → workspace task: fetch + branch
          → chat: scratch directory
  → spawn app-server (cwd = workspace | scratch)
  → initialize → initialized
  → thread/start | thread/resume
  → turn/start
  → for each notification: normalize, batch, POST
  → on approval request: publish, await decision, respond
  → on turn/completed: usage, diff (task only), release
  → on crash: mark orphaned; resume by thread id

The runner is deliberately dumb about product logic. It knows workspaces, processes and protocol — not users, projects or permissions.

Workspace control stays declarative

The dev-server button is a runner job: a fixed start / restart action for a whitelisted command, a process record, logs streamed into the terminal tab, and a port reachable only over the tailnet. Dashboard widgets are a JSON schema; the agent edits data. Neither is a general shell nor arbitrary HTML.

The native Codex app can coexist

Codex's own desktop app can work on the same repository, because files are just files. Conversations are not shared: threads are provider state. Keep the platform's task and event history as the record, store the threadId so you can resume, and treat native-app conversation sync as a separate integration rather than an assumption.

Reconciling the two drafts

PlanDump §5 puts Terminal, file explorer and diff viewer in V1. The HTML moves Terminal, editor and diff viewer to Phase 2. This version resolves it explicitly: live command output, file viewer and diff are V1; an interactive terminal is V1.5; a browser editor is not in scope at all.

Definition of done

  1. The happy path, no SSH. Import a repo, send a prompt, watch the events, approve one command, review the diff, commit. Done from the browser only.
  2. Refresh mid-task. Close the tab while Codex runs. Reopen: the log is complete and still live.
  3. Restart the runner. The task either resumes on the same thread or lands in a clear, recoverable state — never a silent hang.
  4. Deny something. Refuse an approval. The agent stops or adapts, and the audit log records who denied what and when.
  5. Restore. Rebuild the control plane from last night's dump and keep every task, event and decision.
  6. Quick detour. Open a temporary chat with no workspace, get an answer and close it. No branch was created; the scratch directory is gone or was explicitly promoted.
  7. The workspace loop. Open a workspace, start or restart its dev server, open the preview link and a file or diff in the context sidebar, then attach a file to a temporary chat.

  • Day 1 — repo, compose, Postgres, health check
  • Day 2 — login, session, one protected route
  • Day 3 — project CRUD, clone on the runner
  • Day 4 — runner hello world: spawn app-server, initialize
  • Day 5 — thread/start + print every notification
  • Day 6 — events table, batch ingest, WS echo
  • Day 7 — rail shell plus an ugly chat that streams real output

If day seven works, you have de-risked the only genuinely unknown part. Everything after that is CRUD, UI and policy — work you already know how to estimate.

The cut line

If the project stalls, stop after M6. Chat, live events, diff and approvals is already a useful product. Everything below that line is convenience.

08

Infrastructure and security

Two boxes · no inbound ports on the runner ›

The IONOS VPS runs the product. A cheap x86 box runs the code. Keeping those two jobs apart is what makes the whole thing safe and recoverable.

Control plane

IONOS · 2 vCPU · 2 GB

Public or tailnet. Never executes project code.

  • Caddy (TLS)
  • Next.js standalone
  • FastAPI, one worker
  • PostgreSQL 16
  • Nightly dump to object storage
WSS
outbound 443 only

Execution box

x86 · 16 GB · 512 GB

On your desk, behind NAT. Dials out; accepts nothing.

  • Runner service (systemd)
  • 1–2 Codex app-server processes
  • Workspaces on NVMe
  • Docker, no socket exposed to web
  • Per-project secrets, injected at runtime

Does the VPS survive?

With the right settings, yes. The failure mode is not the database — it's running an agent and a Next.js build on the same 2 GB.

ServiceExpected RAMSetting that matters
OS + systemd250–350 MBDisable snapd and anything you don't use.
Caddy~20 MBNothing.
Next.js180–260 MBStandalone output, no build on the server.
FastAPI120–180 MBOne uvicorn worker; no Celery.
PostgreSQL250–350 MBshared_buffers=256MB, max_connections=20.
Swap2 GB (disk)Safety net, not a strategy.

Total: roughly 1.0–1.5 GB resident. Skip Redis, skip a background worker in V1, and never run npm run build on this machine. Add alerts at 80% memory and disk. Dev servers live on the execution box, not here; budget one per active workspace and stop idle ones.

Network shape

  • Tailscale between laptop, control plane and runner. SSH exists only on the tailnet.
  • The runner makes one outbound WSS connection to the API and holds it. Commands, events and approval decisions all travel inside that connection.
  • App-server never listens on a network port. The runner talks to it over stdio; its optional WebSocket listener stays off.
  • Dev servers bind loopback on the runner. Preview links go through the tailnet (or an authenticated Caddy route), never a public port per workspace.
  • Public exposure is optional. If the platform is public, Caddy terminates TLS and rate-limits /api/auth; everything else can stay behind the tailnet.

Security checklist

  • No Docker socket mounted into the web or API container. The runner is the only component allowed to touch Docker.
  • Repo paths are validated against the workspace root on every file request; symlinks are resolved and rejected if they escape.
  • Secrets live in the runner's environment or a file mounted at /run/secrets, never in Postgres, never in events.
  • An event redaction pass strips bearer tokens, API keys and anything matching a secret pattern before persistence.
  • Project policy defaults to “ask” for network and commands outside the workspace; auto-safe is opt-in per project.
  • Containers run as non-root with CPU/memory limits and a per-workspace disk quota; the runner refuses to start a task above the limit.
  • Temporary chats run under /srv/scratch/<id> with a read-only sandbox, no git remote, a 7-day expiry job and no backup.
  • Dashboard documents are validated against a widget schema; props render as text/data, never HTML or JavaScript.
  • Dev-server actions are a whitelisted start / restart per workspace, resource-limited and stopped on idle; the API never forwards arbitrary shell.
  • Every approval writes an audit row with actor, scope, command and timestamp. Deletes are soft.
  • Backups are encrypted and tested. A backup you have never restored is a hope, not a backup.

Hardware and cost

Buy once

A used Lenovo Tiny, Dell Micro or NUC with 16 GB RAM and a 512 GB NVMe: €150–250. x86, Ubuntu LTS, wired Ethernet, a UPS if the power is flaky.

Or rent

A small cloud instance with 8–16 GB (Hetzner CX32 class, roughly €7–9/month) if you don't want hardware at home. You lose the “my repo never leaves the house” argument.

No GPU anywhere. Model inference is remote; this hardware only runs processes, git and tests. Compute the Codex cost separately and cap it per task.

Backup, minimum viable

Nightly pg_dump -Fc to S3-compatible storage; restic snapshots of /srv/workspaces daily; every project has a real git remote; a monthly restore of the database into a scratch container. Three copies, two media, one off-site — of the two things that would actually hurt to lose: task history and repositories. Scratch chats are excluded by design; promote one to a task if it matters.

Risks, open questions, references

What could go wrong · what to decide ›

A plan is only useful if it says where it breaks. These are the failure modes worth designing around before the first line of code, and the decisions that change the shape of V1.

RiskOddsImpactMitigation
App Server protocol driftLikelyMediumPin the Codex version; generate schemas in CI; contract test initialize + one turn against the pinned binary.

Open questions — with a default so you can move

1 · One user, or a few friends?

Changes auth, isolation and the provider-terms story. Multi-user is the largest hidden scope multiplier in the draft.

Defaultsingle user for V1; invite-only magic links later.

2 · ChatGPT plan or API key for Codex?

The plan is cheaper for personal use; a key is cleaner for automation and required if you ever host it for others.

Defaultyour existing plan on the runner's own account; add key support behind config from day one.

3 · Public internet or tailnet only?

Public means TLS, rate limits, brute-force protection and a real auth review. Tailnet means no exposure at all.

Defaulttailnet first; public only when someone else needs it.

4 · Embedded preview, or just a link?

The context rail has a Preview tab. Opening the dev-server URL in a tab is nearly free; proxying the page into the shell is the expensive part.

Defaultopen the link over the tailnet in V1; embedded proxy in V2.

5 · Which second agent?

Claude Code has the closest mental model (streaming JSON, permission prompts, session ids), so it doubles as a test of the adapter contract.

DefaultClaude Code after V1.5 — only if the first adapter has needed no special cases.

6 · How long do you keep event data?

Terminal output and diffs get large; task summaries stay small and useful.

Defaultsummaries forever, raw events 90 days, artifacts 30 days.

7 · What is the spend cap?

A number that is small enough to not hurt and large enough to finish a feature.

Default$2 per task, $20 per day, stop rather than warn.

8 · Where does “done” live?

A task ends at a commit, a PR, or a deployed preview — pick one and make the UI's final button match.

Defaultcommit to the task branch; PR creation in V1.5.

9 · How long should a temporary chat live?

Long enough to come back tomorrow, short enough that it never becomes a hidden project.

Default7 days, no repo, no branch; Keep as task to promote.

10 · How much workspace control should the agent get?

Dashboard widgets and dev-server actions are useful; arbitrary shell is already the runner's job, behind approvals.

Defaultdashboard JSON plus start / restart; the agent cannot author UI code or open public ports.

If you only remember five things

  1. The rail is the home; the task is the product. Persist the events.
  2. Codex is a replaceable process behind an adapter, not the architecture.
  3. The runner is untrusted, outbound-only, and never shares a machine with the API.
  4. Ship read, diff and approve before you ship edit, preview and orchestrate.
  5. Put a hard number on every task's budget from day one.
